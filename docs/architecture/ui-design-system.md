# UI architecture and design system

This document defines the UI source contracts, design tokens, component ownership, and verification standards for Core Habits. The built `styles.css` is generated by Vite and is not an editing surface.

## Ownership map

| Layer | Source | Owns |
|---|---|---|
| Obsidian shell | `src/main.js`, `src/views/WeeklyGridView.js`, `src/views/DailyHabitsSettingTab.js` | View registration, root classes, locale direction, mode and tab state |
| Shared tokens | `src/styles/tokens.css` | Theme aliases, semantic state/progress/streak/level colors, spacing, radius, motion and control sizing inputs |
| Shared button appearance | `src/styles/button.css` | Primary actions, icon/navigation/text buttons, hover/focus/disabled policy and control dimensions |
| Shared row and identity appearance | `src/styles/habit-row.css` | Habit-color scope, row/child paint, type dot, collapse/page controls, child tint, archived appearance and action visibility |
| Color boundary | `src/config/colors.js`, `src/utils/HabitColor.js` | Palette IDs, ID/hex normalization, effective parent inheritance, draft parent/color resolution and passing the color scope to DOM |
| Disclosure primitive | `src/components/ui/CollapseButton.js` | One button DOM, icon, label, `aria-expanded`, `aria-controls` and disclosure state |
| Disclosure coordination | `src/components/ui/GroupCollapseController.js` | Native row visibility, group toggles, serial persistence, save rollback and synchronization of mounted views |
| Shared cell/control states | `src/styles/day-cell.css` | Day cells and compact status controls, semantic completed/skipped/missed paint and interaction |
| Other shared UI | `src/styles/base.css`, `src/components/ui/TabBar.js` | Cards, empty-state defaults, shared audio presentation, tabs and direction-aware tab keyboard/ARIA state |
| Weekly grid structure | `src/styles/grid.css`, `src/views/GridRenderer.js`, `src/views/grid/CompactGridRenderer.js` | Grid columns, header/cell placement, progress structure and renderer routing |
| Weekly layout | `src/styles/weekly-grid-layout.css` | Sticky surfaces, header/toolbar placement, compact flow, spacing and width-dependent layout |
| Settings | `src/styles/settings.css`, `src/views/settings/*`, `src/views/PluginGuideComponent.js` | Settings panels, habit list columns, guide and narrow panel layout |
| Statistics | `src/styles/statistics.css`, `src/views/statistics/*` | Statistics sections, charts, score and habit cards |
| Daily Notes diary | `src/styles/diary-view.css`, `src/views/diary/*` | Diary toolbar, filters, day and entry presentation |
| Modals and popups | `src/styles/modal.css`, `src/modals/*`, `src/components/forms/*` | Habit editor, forms, journey, comment/reflection popups |
| Mobile platform | `src/styles/mobile.css` | Touch sizing inputs on roots and platform-specific chrome/layout, without redefining shared component paint |
| Tooltip adapter | `src/utils/TooltipHelper.js`, Obsidian | Native tooltip attributes and accessible-name semantics; Obsidian/theme owns the rendered tooltip surface |

`src/main.js` imports each of the 13 CSS files once: `tokens`, `base`, `animations`, `button`, `habit-row`, `day-cell`, `grid`, `modal`, `settings`, `statistics`, `diary-view`, `weekly-grid-layout`, `mobile`. `mobile.css` is active. Do not add a catch-all late override sheet. Import order alone does not establish ownership and does not prove precedence over third-party themes.

## Component contracts

- Every plugin view or modal has a `.daily-habits-plugin` root. Feature selectors should also include the feature root or a unique component class. Obsidian notices live outside that root; `.dh-undo-notice` is an intentional exception.
- Buttons use `.dh-btn` where the shared base applies. `button.css` owns shared button paint, control sizes and interactions; `.mod-cta` owns primary semantics and `.dh-btn-hero` changes presentation dimensions. Feature CSS may set placement, gaps and text overflow; it must not redefine shared button colors, borders, hover/focus states or control minima.
- Tabs use `.dh-tabs` and `.dh-tab`; their active state is `.is-active`. Their appearance belongs to `base.css`. `TabBar.js` owns selection, roving `tabIndex`, ARIA attributes and direction-aware keyboard navigation.
- Cards use `.dh-card` for surface, outline and radius. A feature class owns its internal layout and content. `.mod-elevated` adds the shared shadow.
- Habit rows use `.dh-habit` and `.dh-habit-color-scope`. `applyHabitColor()` passes only `--habit-color` from JS. `habit-row.css` derives `--dh-row-color` and its translucent variants on that element, rather than at the root where a later descendant color could not recompute the alias. Weekly and Settings own their different row structures while consuming this same color contract.
- `normalizeHabitColorHex()` accepts a palette ID or resolved six-digit hex. `buildHabitColorMap()` follows the effective hierarchy independently of displayed order/filtering; a missing or inactive parent leaves the child's own identity color. `getFormHabitColorHex()` resolves the draft color/parent rather than reusing persisted parent state. The persisted `color` field remains a palette ID. Palette normalization owns the default fallback; feature renderers must not substitute teal or brand colors when identity propagation fails.
- `CollapseButton` creates the same native button in Weekly Wide, Compact, Settings and Mobile. `HabitRowFactory` delegates to it. The common `data-collapse-id` identifies the group; the component owns its icon, accessible name and expanded state. `aria-controls` links to the child row IDs assigned by the controller. RTL changes the collapsed arrow direction in the shared owner, not in view CSS.
- `GroupCollapseController` applies `row.hidden` and keeps the button semantics in sync. Layout rules that set a row's non-`none` display must include `:not([hidden])`; otherwise author CSS would override the browser's native hidden behavior. There is no view-owned `.is-hidden` or inline `style.display` contract for disclosure rows. Persistence serializes writes, synchronizes registered views and rolls back on save failure. ARIA is an output of component state, not a source of application state.
- State names and tokens are semantic: completed, missed, skipped, pending and today. Change their color definitions in `tokens.css`, then consume them from the component owner. Compact status appearance belongs only to `day-cell.css`. Progress badges use semantic progress tokens; header layout must not neutralize their state colors. Habit identity and completion status are separate color roles.
- Base empty-state and audio appearance belong to `base.css`. A journey or diary variant must be scoped to its actual container; it must not redeclare `.daily-habits-plugin .dh-empty-title` globally. Search indicators are scoped to their search wrapper, so diary layout cannot change settings search layout.
- `TooltipHelper` adapts Obsidian's native tooltip attributes. Clearing a tooltip must not erase an independently required accessible name. Do not add competing `title` tooltips. The native tooltip is outside the row's color scope; its themed background is not a habit identity indicator.
- Empty, loading, error, hover, active, selected, disabled and focus states should have one owner per component. Do not rely on hover to reveal a control on touch screens; keyboard focus and touch access remain visible.

## Tokens and themes

`tokens.css` defines the `--dh-*` token set: semantic brand/state colors, Obsidian surface/text aliases, spacing, typography, radius, shadow, motion and sizing inputs. Feature files may define local layout variables, but shared values should be promoted to `tokens.css` only when at least two owners use them. Product colors for streaks, levels and progress are centralized there. Do not introduce fixed RGB companion values for CSS transparency; use `color-mix()` with the semantic token.

Use Obsidian's `--background-*`, `--text-*`, `--interactive-*` and `--color-*` variables for surfaces and controls. Fixed fallback values in the central token definitions support themes that omit a palette variable. Feature files should not draw their own replacement select arrow or reset native select appearance. Light/dark exceptions are permitted only for demonstrated contrast differences and stay beside the component that needs them.

Use logical CSS properties (`padding-inline-start`, `margin-inline-end`, `border-inline-start`) for direction-dependent geometry. The root `dir` comes from `TranslationManager`; direction-aware keyboard behavior is in `TabBar.js`. Avoid separate RTL copies of layout rules unless a genuine direction-specific visual remains.

## Responsive rule

The same Weekly, Settings, Statistics and Diary components serve desktop, narrow side panes and mobile. Each view owns its `container-type: inline-size` boundary. Weekly also gives its parent content element `.dh-weekly-query-host`, so a query can size the weekly root itself. Use `@container` for available-pane width and `body.is-mobile` for platform behavior such as touch targets or modal chrome. Current width thresholds are component-specific, not device labels.

Responsive rules change component sizing inputs on the owning root, not the size declarations or color rules on shared controls. Controls compute their dimensions as the maximum of the ordinary size and the applicable touch minimum. This prevents a narrow layout declaration from defeating mobile minima through greater selector specificity. Keep hover/focus/disabled semantics in the component owner across breakpoints. Native disclosure visibility must survive every container query.

## Change procedure

1. Identify the component's DOM owner and the CSS owner in the map above.
2. Change a shared token or primitive once when the visual meaning is shared; otherwise change the feature owner.
3. Check narrow widths, Arabic RTL, English LTR, light/dark themes, keyboard focus and touch-visible actions for that component.
4. Run `npm run ui:check`, `npm run lint`, `npm run typecheck`, `npm run test:run` and `npm run build` before release review.
5. In Obsidian, verify Settings, Weekly grid, compact grid, Statistics, Diary, editor and popups at a full window, a narrow side pane and mobile portrait/landscape. Verify completed/missed/skipped/empty/loading/error/disabled states and an existing vault with legacy notes. Automated DOM tests and CSS parsing do not replace this visual and runtime check.

## Automated architecture gate

`scripts/check-ui-css.mjs` checks parse validity, one import per stylesheet, defined `--dh-*` references, and these migrated ownership boundaries:

- Collapse and habit-color-scope paint only in `habit-row.css`.
- Compact status-control paint and sizing only in `day-cell.css`.
- Icon/navigation/text control paint, sizing and interactions only in `button.css`.
- Habit/child row paint only in `habit-row.css`; a list header is a separate component, and a sticky descendant cell can keep its layout surface in a view.
- Row layout cannot override native disclosure hiding through an unguarded display rule.
- No exact duplicate selector/property declarations in the same conditional context for these components or shared empty/search/audio selectors, including duplicates in the same file.
- No `!important` on the migrated components.

Separate `@media`/`@container` contexts and explicitly scoped feature variants are legitimate. Unrelated legacy components are outside this targeted gate. The check is intentionally stricter than a CSS parser and narrower than a whole-project ban on repeated selectors. It cannot model browser cascade layers, shorthand overlap, selector equivalence, theme injection or the final computed appearance.
## Runtime verification and visual inspection

Automated DOM tests and CSS static validation provide essential regression coverage but cannot substitute for live visual validation inside Obsidian.

Before releasing updates, perform live manual verification across the following dimensions:
1. **Appearance & Themes**: Verify matched and computed colors, surface backgrounds, borders, focus outlines, and box shadows in both Default (Dark & Light) and popular community themes (such as Blue Topaz or Minimal).
2. **Localization & Direction**: Verify layout flow, logical margins/paddings, and icon directions in both Arabic (RTL) and English (LTR).
3. **Responsive Widths**: Test the Weekly grid, Settings, Statistics, and Diary across full-width desktop views, narrow side panes (300px, 500px, 580px container queries), and mobile portrait/landscape.
4. **Interactive States**: Validate idle, hover, focus-visible, active, collapsed, and disabled states across Wide, Compact, and Settings views. Ensure hidden group rows remain collapsed, controls remain reachable, and tooltip/ARIA names remain synchronized.
